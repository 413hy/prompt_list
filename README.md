# 常用 Prompt 合集

> 说明  
> 1. 这是适合直接放到 GitHub Markdown 文档里的版本。  
> 2. GitHub 会给代码块自动提供复制按钮，所以每个 Prompt 都单独放在代码块中。  
> 3. 每个 Prompt 下面都单独列出该 Prompt 的变量，方便替换。  
> 4. 涉及账号、密码、Token 的内容，建议始终使用占位符，不要把真实密钥直接提交到仓库。  
> 5. 所有 Synque 相关 Prompt 都应显式带上 email / pass / DIRECTUS_PRD_ENDPOINT / DIRECTUS_PRD_TOKEN，否则很容易因为缺少登录信息而失败。

## 1. w-代码提交前检查 + 自动提交 + 发起 PR

### Prompt
```text
【变量区】
- <CURRENT_BRANCH> = （可留空；优先自动从当前 git 分支获取）
- <TARGET_BRANCH> = （可留空；优先自动从仓库默认分支或项目约定中获取）

【自动发现规则】
1. 如果变量未提供，请优先从当前工作区、仓库配置、README、需求文档、已有 cards / stories / spec 中自动查找。
2. 如果有多个候选值，请选择与当前变更最相关的一个，并说明判断依据。
3. 如果无法可靠确定，再明确指出缺失项，不要假装已完成。

【理解优先规则】
1. 在开始检查、提交、创建 PR 之前，请先确认你已经真正理解我的需求、当前上下文、目标分支、变更范围和执行边界。
2. 如果存在任何不明确、歧义、上下文不足、候选项冲突、风险判断依据不足的地方，请先停下来向我提问，不要直接实施。
3. 提问时一次只问一个问题。
4. 根据我的回答继续追问，直到你对我的真实需求、目标、边界条件和执行前提有至少 95% 的把握，再继续后续操作。
5. 在没有达到这个理解程度之前，不要直接提交代码、不要直接创建 PR，也不要假设你已经理解正确。

【任务】
请先使用可用的 skills / tools，对我当前工作区和待提交代码做一次完整检查，再决定是否执行提交与 PR。

任务目标：
1. 检查当前分支上的所有待提交代码，确认是否符合当前仓库规范、项目要求、已有需求文档 / 任务卡片 / 用户故事 / 流程约束。
2. 重点检查：
   - 功能是否完整
   - 是否存在明显 bug、边界场景遗漏、回归风险
   - 命名、目录结构、注释、可维护性是否合理
   - 权限、数据隔离、接口调用、状态处理、异常处理是否存在问题
   - 是否存在 lint、type、test、build、依赖、安全风险
   - 实现是否与已有需求和验收标准一致
3. 输出检查结论：
   - `PASS`
   - `BLOCKED`
4. 如果是 `BLOCKED`，请列出必须先修复的问题，并按优先级排序。
5. 如果是 `PASS`，请直接继续执行：
   - 提交当前变更
   - 生成规范的 commit message
   - 发起到目标分支的 PR
6. 如果无法直接执行 git commit / push / 创建 PR，请不要假装已完成；请输出：
   - 建议的 commit message
   - PR title
   - PR description
   - 我只需要复制执行的最短命令

输出格式：
- 检查范围
- 风险结论（PASS / BLOCKED）
- 发现的问题
- 建议的 commit message
- 建议的 PR 标题与描述
- 如不可执行则给出下一步最短操作命令
```

### 变量
- `<CURRENT_BRANCH>`：当前工作分支，例如 `feat-uploadpage`
- `<TARGET_BRANCH>`：目标分支，例如 `init-ai`

## 2. w-基于已有 Cards / Stories 生成新的 User Story 文档

### Prompt
```text
【变量区】
- <NEW_STORY_REQUIREMENT> = 这里写本次新增需求

【自动发现规则】
1. 除了 `<NEW_STORY_REQUIREMENT>` 以外，其余上下文请优先从当前工作区自动查找，包括：
   - cards
   - stories
   - spec / PRD / design doc
   - policy / validation / business rules
   - 相关模块、页面、流程
2. 如果上下文不足，请基于现有材料做合理补全，并明确标出假设项。

【理解优先规则】
1. 在开始撰写 User Story 之前，请先确认你已经真正理解我的需求、业务目标、适用范围、依赖上下文和验收方向。
2. 如果存在任何不明确、歧义、规则冲突、上下文不足或需求边界不清的地方，请先停下来向我提问，不要直接开始写文档。
3. 提问时一次只问一个问题。
4. 根据我的回答继续追问，直到你对我的真实需求、目标、文档用途、约束条件和验收预期有至少 95% 的把握，再开始撰写。
5. 在没有达到这个理解程度之前，不要直接输出最终文档，也不要把关键假设当成既定事实。

【任务】
请先使用可用的 skills / templates，根据当前项目中已有的需求材料风格与结构，帮我写一份新的 User Story 文档。

请你完成以下内容：
1. 先理解并继承已有需求材料的上下文、命名风格与文档结构。
2. 输出一份结构完整、可直接落地的新 User Story 文档。
3. 文档中至少包含：
   - Title
   - Background / Context
   - User Story
   - Scope
   - Acceptance Criteria
   - Validation Rules
   - Error / Edge Cases
   - Dependencies / Related Items
   - Out of Scope
4. Acceptance Criteria 必须清晰、可测试、可验收。
5. 请覆盖：
   - 用户操作前置条件
   - 用户操作流程
   - 成功条件
   - 失败提示
   - 取消 / 中断 / 空状态处理
   - 边界情况与异常情况
6. 请使用偏产品 / 交付文档的语言，不要写成纯代码说明。
7. 最终请输出为一份可直接保存为 `.md` 的文档内容。

输出要求：
- 结构清晰
- 表达一致
- 验收明确
- 能直接作为后续开发与测试依据
```

### 变量
- `<NEW_STORY_REQUIREMENT>`：- <NEW_STORY_REQUIREMENT> = 这里写本次新增需求

## 3. w-将指定 Card 文档同步到 Synque（必须携带环境变量）

### Prompt
```text
【变量区】
- <SOURCE_ITEM> = 需要同步的源文档 / 卡片 / 故事 / 文件
- <TARGET_SYSTEM> = 目标系统名称
- <AUTH_CONTEXT> = （可留空；如工作区或配置中已有相关账号、token、endpoint、author 等信息，则优先自动发现并使用）

【自动发现规则】
1. 如果 `<AUTH_CONTEXT>` 未提供，请优先从以下位置自动查找：
   - `.env*`
   - 配置文件
   - README / 接入文档
   - 已有同步脚本 / 集成脚本
   - 当前仓库中与目标系统相关的代码
2. 如果找到多个候选值，请选择与当前项目环境最匹配的一个，并说明依据。
3. 如果敏感信息不存在，不要编造，直接指出缺失项。
4. 在整个登录、读取、校验、同步过程中，优先使用显式传入的变量；若为空，再使用自动发现结果。

【理解优先规则】
1. 在开始登录、校验、同步之前，请先确认你已经真正理解我要同步的对象、目标系统、同步目的、字段要求、认证方式和执行边界。
2. 如果存在任何不明确、歧义、上下文不足、字段映射不清、认证信息可疑、环境不确定或目标系统规则不明确的地方，请先停下来向我提问，不要直接同步。
3. 提问时一次只问一个问题。
4. 根据我的回答继续追问，直到你对我的真实需求、目标系统要求、认证前提、字段映射关系和执行条件有至少 95% 的把握，再继续实施。
5. 在没有达到这个理解程度之前，不要假设已经登录、不要假设字段可以自动映射成功，也不要假装同步已完成。

【任务】
请优先使用可用的 skills / tools，帮我把 `<SOURCE_ITEM>` 同步到 `<TARGET_SYSTEM>`，并在执行前先做一次完整校验。

执行要求：
1. 先读取并理解 `<SOURCE_ITEM>` 的内容。
2. 检查格式、字段完整性、标题、描述、验收标准、关联信息是否满足 `<TARGET_SYSTEM>` 的同步要求。
3. 如果发现缺失项、字段错误、格式问题或不一致项，先列出问题并修正建议，再决定是否继续同步。
4. 同步过程中不要省略认证信息，也不要假设已经登录。
5. 同步时尽量保留作者、来源、标签、状态等关键信息（如果适用）。
6. 同步完成后，返回：
   - 是否成功
   - 同步后的对象名称 / ID / 链接（如果可获得）
   - 最终写入的关键字段摘要
7. 如果无法直接执行同步，请不要假装已完成；请输出：
   - 手动执行步骤
   - 每一步的预期结果
   - 最容易出错的检查点
8. 如果登录或同步失败，请明确指出：
   - 认证信息是否缺失
   - 环境变量是否缺失或格式错误
   - Token 是否失效或权限不足
   - Endpoint / API 地址是否错误
   - 当前环境是否不支持直接执行相关 skill / tool

输出风格：
- 简洁
- 可执行
- 先校验，后同步
- 不要跳过失败检查
```

### 变量
- <SOURCE_ITEM>：源文档 / 卡片 / 故事 / 文件
- <TARGET_SYSTEM>：目标系统名称
- <AUTH_CONTEXT>：认证与环境变量信息块，可选

### 使用时替换示例（不要把真实值提交到仓库）
```text
<AUTH_CONTEXT> =
- email: your_email
- pass: your_password
- API_ENDPOINT: your_endpoint
- API_TOKEN: your_token
- Author: your_name
```

## 4. w-对齐工作区项目功能、Cards、Stories、Synque 的一致性

### Prompt
```text
【变量区】
- <CHECK_SCOPE> = （可留空；优先自动从当前工作区和本次需求上下文中识别）
- <AUTH_CONTEXT> = （可留空；如涉及外部系统登录、读取、查询、同步，则优先从工作区或配置中自动发现）

【自动发现规则】
1. 如果 `<CHECK_SCOPE>` 未提供，请根据当前工作区、代码变更、模块目录、文档上下文自动识别相关范围。
2. 如果涉及外部系统，请优先从 `.env*`、配置文件、README、同步脚本中自动查找认证信息。
3. 如果无法可靠确定，不要假装已对齐完成，直接指出缺失项。

【理解优先规则】
1. 在开始一致性对齐之前，请先确认你已经真正理解我要核对的范围、相关需求来源、外部系统对象、验收标准和对齐目标。
2. 如果存在任何不明确、歧义、上下文不足、范围边界不清、来源不一致、外部系统对象不明确或认证条件不清的地方，请先停下来向我提问，不要直接开始对齐。
3. 提问时一次只问一个问题。
4. 根据我的回答继续追问，直到你对我的真实需求、对齐目标、核对范围、判断标准和执行前提有至少 95% 的把握，再继续实施。
5. 在没有达到这个理解程度之前，不要直接给出最终对齐结论，也不要把推测当成事实。

【任务】
请优先使用可用的 skills / tools，帮我做一次一致性对齐检查，范围包括：
- 当前工作区 / 项目代码实现
- 需求文档 / 用户故事 / 任务卡片
- 外部系统 / 同步系统中的相关记录
- 其他与当前需求有关的关键上下文

目标：
确认“实现、文档、卡片、系统记录、验收标准”这几部分是否表达一致、实现一致、状态一致、验收一致。

请按以下步骤完成：
1. 梳理当前项目实际实现了哪些功能，以及每个功能的边界。
2. 对照需求文档 / 用户故事 / 任务卡片，检查是否存在：
   - 文档有但实现没有
   - 实现有但文档没写
   - 命名不一致
   - 流程不一致
   - 验收条件不一致
   - 依赖关系不一致
   - 状态不一致
3. 再把上述结果与外部系统 / 同步系统中的内容做一次对齐。
4. 如果涉及外部系统，不要跳过登录或假设已经登录。
5. 对每个不一致项给出：
   - 类型
   - 影响范围
   - 建议修复方式
   - 优先级
6. 最后输出：
   - 已对齐项
   - 未对齐项
   - 建议优先修复项
   - 修复后还需要复查的内容
7. 如果外部系统无法访问，请明确指出：
   - 凭据缺失
   - Endpoint / API 配置错误
   - Token 无效或权限不足
   - 当前环境无法执行相关 skill / tool

输出格式：
- 表格：列出不一致项
- 简明结论：说明整体对齐状态
- 优先级建议：说明先修什么
```

### 变量
- `<CHECK_SCOPE>`：检查范围，可选
- `<AUTH_CONTEXT>`：外部系统认证信息块，可选

### 使用时替换示例（不要把真实值提交到仓库）
```text
<AUTH_CONTEXT> =
- email: your_email
- pass: your_password
- API_ENDPOINT: your_endpoint
- API_TOKEN: your_token
- Author: your_name
```

## 5. 一步一步指导模式（可追加到其他 Prompt 后面）

### Prompt
```text
交互要求：
1. 请一步一步地指导我完成，不要一次输出很多步骤。
2. 每一轮只告诉我“当前最应该做的下一步”。
3. 等我执行完并把结果返回给你后，你再继续给我下一步。
4. 如果我返回的结果有问题，请先帮我判断问题原因，再给我新的下一步。
5. 每次回复尽量简短、明确、可直接执行。
6. 除非我主动要求，否则不要一次给出完整方案。
```

### 变量
- 无固定变量  
- 建议作为附加模板，直接拼接到其他 Prompt 末尾使用

## 6. 苏格拉底反问完成需求

### Prompt
```text
在回答或给出方案之前，请先通过提问充分理解我的真实需求。

请严格遵守以下规则：
1. 先问问题，不要直接给答案或方案。
2. 每次只问一个问题。
3. 等我回答后，再根据我的回答继续追问下一个最关键的问题。
4. 你的问题要尽量简短、明确、聚焦，优先确认目标、约束、场景、预期结果和成功标准。
5. 如果我的描述含糊、存在歧义、信息不足或前后矛盾，请继续追问，不要自行脑补。
6. 在你对我的真实需求、目标、边界条件和期望输出形式达到至少 95% 的把握之前，不要进入方案阶段。
7. 当你认为信息已经足够时，先用简短的话总结你对我需求的理解，并请我确认。
8. 只有在我确认你的理解基本正确后，你再开始给出方案。
9. 给出方案时，请确保方案与我们前面的问答内容严格一致，不要偏题，也不要遗漏我明确提出的要求。

你的整体沟通方式要求：
- 一轮只做一件事：要么提一个问题，要么在确认后给方案。
- 不要一次抛出多个问题。
- 不要提前输出大段分析。
- 不要用模板化、敷衍式追问。
- 以帮助你准确理解我的真实目标为最高优先级。
```

### 变量
-  苏格拉底问法

## 7. 苏格拉底式理解概念

### Prompt
```text
【变量区】
- <CONCEPT_SET> = 这次要学习的一组概念
- <FOCUS_POINTS> = （可留空；如果你特别想弄懂某几个点、某几组关系，写在这里）

【任务】
我想学习一组专业概念，但我不希望你一上来就直接长篇讲解，也不希望你直接把最终答案全部灌输给我。

这次请你带我理解这些概念：
`<CONCEPT_SET>`

如果我提供了特别关注点，请额外重点照顾这些部分：
`<FOCUS_POINTS>`

请严格按照下面的流程来进行：

【第一阶段：先给我一个全景式小总结】
1. 先不要展开细讲。
2. 先用通俗、简洁的方式，给我一个“小总结”或“全景图”：
   - 这些概念分别大概是做什么的
   - 它们之间大概是什么关系
   - 哪些地方最容易混淆
3. 这一部分只需要帮我建立整体感觉，不要讲太深，不要堆太多术语。
4. 小总结结束后，请主动问我：
   - 我目前最不清楚的是哪几个点
   - 我最想先弄懂哪一组概念关系
   - 我觉得自己已经懂了哪些，哪些还模糊

【第二阶段：根据我的困惑，用苏格拉底式提问引导我理解】
5. 从我最困惑的地方开始引导，而不是你自己按固定顺序硬讲。
6. 你的主要方式应当是“提问引导”，不是“直接公布答案”。
7. 每次只问我一个问题。
8. 根据我的回答，继续追问、纠正、引导，帮助我自己一步步想明白。
9. 如果我答得不准确，不要直接否定我，而是通过问题、类比、场景提示，引导我发现自己哪里理解偏了。
10. 在必要时，你可以给我少量提示，但不要一次讲太多。
11. 如果你发现我已经理解了某一部分，可以让我用自己的话复述一遍，帮助我巩固。

【第三阶段：控制讲解节奏】
12. 不要一次性讲完整套知识。
13. 每次只推进一个小点或一个容易混淆的问题。
14. 每解决一个小点后，用一句很短的话帮我做阶段性小结，然后继续问我下一个问题。
15. 尽量结合真实场景来引导；如果是技术概念，就优先结合真实系统、产品、网站、接口、用户行为、数据流转等场景来解释。
16. 全程尽量用通俗语言，不要一开始就堆专业术语。

【第四阶段：达到大约 90% 理解后再总结】
17. 在我还没有明显理解到位之前，不要急着做最终总结。
18. 先通过问答确认我的理解程度。
19. 当你判断我已经理解到大约 90% 时，再给我做一个最终总结。
20. 最终总结需要包含：
   - 每个概念的一句话解释
   - 它们之间的关系
   - 它们最核心的区别
   - 最容易混淆的点
   - 一个简洁的对比表，帮助我区分这些概念
21. 最终总结要简洁、清楚、便于记忆，不要写得太厚重。
```
